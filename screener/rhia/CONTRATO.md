## Módulos do núcleo (`screener/rhia/`) — edge-only, runtime-agnóstico (Web Crypto, sem `node:` exceto nos testes)

`definicao.mjs` exporta: `instrumento` (o JSON importado com `{ type: "json" }` — Deno e node aceitam), `checksum()` async (sha256 via `crypto.subtle` sobre `canonicalize` — ATENÇÃO: `../motor/definicao.mjs` importa `node:crypto`; portanto `canonicalize` é reimplementado localmente em `definicao.mjs` com a MESMA regra (objeto: chaves ordenadas; array: ordem) e a igualdade é provada nos testes contra a função do motor), `GRUPOS = [{code:"contexto",name:"Contexto"},{code:"praticas",name:"Práticas"},{code:"governanca",name:"Governança"}]`, `apresentacaoPublica()` → `{ instrument:{id,version,title,purpose,disclaimer,estimated_minutes:"8–10"}, groups, items:[{id,order,kind,group,dimension_name?,prompt,options:[{id,label}],conditional_field?}] }` onde `group` = contexto (kind context) | praticas (scored) | governanca (governance_gate); `dimension_name` = nome humano da dimensão do JSON (`instrument.dimensions[].name`) só para scored; `conditional_field` copiado do JSON quando existir. NADA de scale/facet/scenario/pesos na apresentação. Ordem = campo `order`.

`logica.mjs` exporta: `ITENS_IDS` (30 ids), `validarResposta(item_id, value, def)` → lança `Error` com mensagem `"opcao_invalida"|"texto_invalido"` se inválido (regras: scored/gate: value ∈ {E1,E2,E3,E4,NA}; context: value ∈ options[].id; item_id `"CTX01_OTHER_TEXT"`: string trim 2–120 chars, sem caracteres de controle (regex `/[\u0000-\u001f\u007f]/`), só válido quando CTX01=OTHER — a validação server de coerência CTX01/OTHER_TEXT fica no `validarSubmissao`); `validarSubmissao(respostas)` → lança `"incompleto: falta X"` para qualquer um dos 30 ids ausente, `"texto_obrigatorio"` se `CTX01==="OTHER"` e `CTX01_OTHER_TEXT` ausente/inválido, `"itens_estranhos"` para chaves fora dos 30 ids + `CTX01_OTHER_TEXT`; `canonico(respostas)` = chaves ordenadas por code unit (`sort()` padrão), cada linha `item + "\t" + value`, unidas por `"\n"` (idêntico ao SQL: `string_agg(item_code||E'\t'||answer_code, E'\n' order by item_code collate "C")`); `respostasParaMotor(respostas)` → `{ ...respostas }` SEM a chave `CTX01_OTHER_TEXT` (o motor só lê ids do instrumento; o texto livre não pontua); `paraPublico(contrato)` → `contrato.public` acrescido de `emitido_em` (YYYY-MM-DD derivado de `contrato.internal.generatedAt`) — e NUNCA inclui `contrato.internal`. Também exporta `calcularContrato({instrumento, respostas})` = `buildResultContractV2({ instrument: instrumento, answers: respostasParaMotor(respostas) })` importando de `./pacote/src/output-engine-v2.mjs`.

Testes do núcleo (`node --test` em `screener/rhia/`): apresentação tem 30 itens na ordem, sem chaves proibidas (scale, facet, weights, bp), literalidade (prompt/labels idênticos ao JSON), `conditional_field` presente em CTX01; validações (cada ramo de erro); canônico determinístico e independente da ordem de inserção; `paraPublico` sem internal, sem "bp", sem 3333/6667; checksum hex64 estável e IGUAL a `createHash sha256` de `canonicalize` do motor (`node:crypto` no teste); `fronteira-rhia.test.mjs`: nenhum arquivo em `frontend/` (publish dir do `netlify.toml`) contém os prompts (primeiros 40 chars) nem os ids de item do instrumento rhia nem `"boomit_rh_ia_maturity_v1"` — as questões chegam pela edge.
